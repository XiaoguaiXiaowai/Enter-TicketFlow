# 企业客服工单平台迭代计划

## 0 文档说明

本计划依据[技术架构](architecture.md)拆分交付单元。每个迭代结束都产出一个可以独立部署、独立验证的功能块，不依赖后续迭代才能运行。迭代内部的任务按依赖排序，任务完成后必须走验收登记，未登记的任务不计入完成。

本计划不规定日期和人力投入，只规定交付顺序、任务边界、验证方式和验收标准。

## 1 验收与登记机制

### 1.1 任务状态

| 状态 | 含义 | 进入条件 |
|---|---|---|
| 未开始 | 尚未开发 | 迭代启动时的默认状态 |
| 开发中 | 正在实现 | 前置任务已验收 |
| 待验收 | 开发完成，等待验收 | 自测通过，验证清单全部勾选，提交证据 |
| 已验收 | 验收通过 | 验收人复核证据并确认标准达成 |
| 已驳回 | 验收不通过 | 验收人填写驳回原因，任务回到开发中 |

状态只能按箭头方向流转：未开始 → 开发中 → 待验收 → 已验收，待验收可被驳回回到开发中。跳过"待验收"直接标记完成视为登记无效。

### 1.2 验收登记字段

每个任务完成后，在所属迭代的验收登记表中新增一行，字段含义固定：

| 字段 | 填写要求 |
|---|---|
| 任务编号 | 与任务标题一致，如 `I2-T4` |
| 提交人 / 日期 | 实际完成开发的人与提交日期 |
| 变更集 | 提交 SHA 或 PR 链接；镜像类任务填镜像标签 |
| 验证环境 | 本地 Compose、CI 临时环境或预发环境，三选一并写明地址 |
| 验证方式 | 执行的命令、访问的页面或调用的接口 |
| 证据 | 测试报告、Playwright trace、截图、SQL 查询结果、日志片段的可访问链接 |
| 结论 | 通过 / 不通过 |
| 验收人 / 日期 | 非提交人本人；迭代内任务可由同组工程师互验，迭代出口由负责人验收 |
| 备注 | 驳回原因、遗留问题或后续跟进项 |

证据必须可复核。只写"已验证"而没有命令输出或报告链接的登记，按未登记处理。涉及权限、幂等、并发的任务，证据中必须包含反向用例的结果，例如越权请求返回 403 的响应体、重复提交后列表只有一条记录。

### 1.3 迭代出口标准

迭代只有在以下条件全部满足时才算交付。任何一项不满足，迭代保持开放，不允许启动下一个迭代的功能开发。

1. 迭代内全部任务状态为已验收，登记表无空行。
2. 从干净数据库执行 `prisma migrate deploy` 成功，重复执行不报错。
3. `docker compose up -d --build` 后所有服务健康，`/health/ready` 返回 200。
4. 本迭代新增的 Playwright 用例在 CI 中通过，历史用例无回归失败。
5. 本迭代涉及的接口在 OpenAPI 文档中可见，字段与实现一致。
6. 部署与验证步骤写入迭代的"独立部署验证"小节，且由验收人按步骤复跑一次。

### 1.4 任务验证清单的写法

每个任务的验证清单由三类条目组成：功能条目验证主路径，边界条目验证异常输入，安全条目验证越权或数据泄露。验收标准必须可判定，写清返回码、数据条数、页面状态或耗时，不使用"正常""符合预期"这类无法复核的表述。

## 2 迭代总览

| 迭代 | 功能块 | 独立可验证的结果 | 依赖 |
|---|---|---|---|
| I0 | 工程基座与部署骨架 | 空应用可部署，健康检查通过，CI 三阶段可跑 | 无 |
| I1 | 认证、租户与权限 | 两个租户可登录，跨租户访问被拒，字段按角色投影 | I0 |
| I2 | 工单核心与审计 | 可建单、回复、流转；重复提交不重复建单；并发更新返回 409；审计可查 | I1 |
| I3 | 知识库与回复模板 | 草稿可编辑、发布后生效；检索只返回已发布内容；模板变量校验生效 | I2 |
| I4 | 运行加固与交付 | 限流、降级、告警、备份恢复、性能预算与全量回归通过 | I3 |

迭代之间的依赖只体现在数据库结构与权限模型上。I1 完成后，I2 的接口可以独立部署验证；I3 不修改工单核心行为；I4 只增加运维能力，不改变业务接口语义。

## 3 I0 工程基座与部署骨架

### 3.1 迭代目标

把仓库、构建、数据库迁移、容器编排和 CI 立起来。迭代结束时没有任何业务功能，但任意一台装有 Docker 的机器可以用一条命令拉起系统，健康检查通过，CI 能在 PR 上跑完静态检查与数据库迁移校验。

### 3.2 交付边界

包含：工作区结构、NestJS 与 React 构建骨架、Prisma 迁移机制、Docker Compose 编排、Nginx 静态托管、健康检查、GitHub Actions 三阶段流水线。

不包含：任何登录、工单、知识库功能；业务表只建迁移基线和扩展，不建业务实体。

### 3.3 独立部署验证

```bash
cp .env.example .env
docker compose --profile tools run --rm migrate
docker compose up -d --build
curl -i http://localhost/api/health/live
curl -i http://localhost/api/health/ready
curl -i http://localhost/
```

验证人应看到：`/health/live` 返回 200；`/health/ready` 返回 200 且响应中包含迁移版本；根路径返回前端页面而不是 404；`docker compose ps` 中 `postgres`、`redis`、`api`、`worker`、`web`、`nginx` 均为 healthy 或 running。

### 3.4 任务

#### I0-T1 建立工作区与工程规则

- 内容：pnpm workspace 结构（`apps/api`、`apps/web`、`packages/shared`），统一 TypeScript 配置、ESLint、Prettier、提交前检查脚本，`.env.example` 列出全部配置键。
- 依赖：无。
- 验证清单：
  - [ ] `pnpm install --frozen-lockfile` 在干净目录成功。
  - [ ] `pnpm lint` 与 `pnpm typecheck` 对空项目返回 0。
  - [ ] 修改一处类型错误后 `pnpm typecheck` 能报错并指出文件行号。
  - [ ] `.env.example` 的每个键与配置 schema 中的键一一对应。
- 验收标准：三个命令全部退出码 0；仓库中不出现真实密钥；新增配置键必须同时出现在 schema 与示例文件，缺一即不通过。

#### I0-T2 API 骨架与配置校验

- 内容：NestJS 应用入口、模块目录结构、全局异常过滤器、结构化日志、配置 schema 校验、`/health/live` 与 `/health/ready`。
- 依赖：I0-T1。
- 验证清单：
  - [ ] 缺少必填环境变量启动时进程退出，日志打印缺失的键名。
  - [ ] `/health/live` 不依赖数据库，数据库停止时仍返回 200。
  - [ ] `/health/ready` 在数据库不可用时返回 503。
  - [ ] 未捕获异常返回 500 且响应体只含 `error.code`、`message`、`requestId`，不含堆栈。
- 验收标准：四个场景的结果与上述一致；日志为单行 JSON，包含 `requestId`、`route`、`statusCode`、`durationMs`。

#### I0-T3 数据库基线、迁移与种子框架

- 内容：Prisma schema 基线、`prisma/migrations` 目录、迁移执行说明、seed 脚本框架、`app_rw`、`app_migrator`、`app_worker` 三个数据库角色的初始化脚本。
- 依赖：I0-T2。
- 验证清单：
  - [ ] 空库执行 `prisma migrate deploy` 成功。
  - [ ] 同一命令重复执行不报错、不重复建表。
  - [ ] `prisma migrate diff` 在 schema 与迁移一致时退出码为 0。
  - [ ] 三个数据库角色均可连接，`app_rw` 执行 DDL 被拒绝。
- 验收标准：迁移可在空库一次通过；角色权限测试结果符合预期；迁移目录与 schema 无差异。

#### I0-T4 前端骨架与静态托管

- 内容：React + TypeScript + 路由骨架、API 客户端封装、构建产物由 Nginx 托管并回退 `index.html`，`/api` 反向代理到后端。
- 依赖：I0-T1。
- 验证清单：
  - [ ] `pnpm build` 产出静态文件，镜像中不包含源码。
  - [ ] 直接访问 `/tickets/123` 返回页面而不是 404。
  - [ ] 浏览器请求 `/api/health/ready` 经 Nginx 转发成功。
  - [ ] 页面加载不出现控制台报错和 404 资源。
- 验收标准：刷新任意前端路由均能打开；静态资源带缓存头，`index.html` 不带长缓存。

#### I0-T5 Compose 编排与启动顺序

- 内容：`docker-compose.yml` 定义 nginx、web、api、worker、postgres、redis、migrate；健康检查、命名卷、依赖条件、`tools` profile。
- 依赖：I0-T2、I0-T3、I0-T4。
- 验证清单：
  - [ ] `docker compose up -d --build` 后 `docker compose ps` 全部服务为 running。
  - [ ] `migrate` 未执行时 `api` 不就绪，就绪检查返回 503。
  - [ ] 执行 migrate 后 `api` 转为就绪，无需重启容器。
  - [ ] 删除数据卷重新拉起，流程仍可完成。
- 验收标准：从空卷到全服务健康的过程可重复三次且结果一致；不存在手工建库或手工建表的步骤。

#### I0-T6 CI 基线与分支保护

- 内容：GitHub Actions 的 `static`、`integration`、`e2e` 三个 job，PostgreSQL service、迁移校验、Playwright 安装与失败产物上传。
- 依赖：I0-T1、I0-T3、I0-T5。
- 验证清单：
  - [ ] PR 触发 `static` 与 `integration`，两者通过后 `e2e` 执行。
  - [ ] 故意提交类型错误，流水线在 `static` 阶段失败。
  - [ ] 故意修改 schema 不生成迁移，`migrate diff` 步骤失败。
  - [ ] 失败时 `playwright-report` 作为 artifact 可下载。
- 验收标准：三项检查设为 `main` 分支必需检查；失败原因的日志可直接定位到步骤，不需要登录服务器排查。

## 4 I1 认证、租户与权限

### 4.1 迭代目标

建立身份与隔离基座。迭代结束时可以登录两个不同租户，同一用户在不同租户拥有不同角色；页面按权限隐藏入口只是表现形式，直接调用接口同样会被拒绝；字段级权限在响应中生效，未授权字段不出现。

### 4.2 交付边界

包含：用户、会话、登录与刷新、租户与项目、成员与角色、权限求值与字段策略、RLS 策略、前端登录与租户切换、越权测试套件。

不包含：工单、知识库业务；审计写入（I2 引入）；限流与登录锁定（I4 完善）。

### 4.3 独立部署验证

```bash
# 1. 迁移并写入演示租户与角色
docker compose --profile tools run --rm migrate
docker compose --profile tools run --rm seed

# 2. 登录租户 A 的客服账号
curl -i -c /tmp/a.cookie -X POST http://localhost/api/v1/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"email":"agent-a@example.com","password":"<seed 密码>","tenantCode":"tenant-a"}'

# 3. 读取权限摘要
curl -s -b /tmp/a.cookie http://localhost/api/v1/me/permissions
```

验证人应看到：登录返回 200 并写入 refresh Cookie；权限摘要中的角色与字段策略与 seed 一致；用租户 A 的 token 请求租户 B 的项目资源返回 404；外包角色的响应中不包含 `internalNote` 与 `refundAmount`；未登录请求 `GET /v1/me/permissions` 返回 401。

### 4.4 任务

#### I1-T1 用户、密码与会话存储

- 内容：`users`、`sessions` 表；Argon2id 密码哈希；会话包含 `token_version`、refresh 摘要、设备信息、撤销时间。
- 依赖：I0 出口。
- 验证清单：
  - [x] 数据库中不出现明文或可逆密码，哈希前缀为 Argon2id。
  - [x] 同一密码两次注册产生不同哈希。
  - [x] 撤销会话后 `token_version` 递增，旧 access token 立即失效。
  - [x] 会话到期后刷新接口返回 401。
- 验收标准：四项均可在集成测试中复现；撤销后 1 秒内旧 token 无法访问任何受保护接口。

#### I1-T2 认证接口与刷新轮换

- 内容：`POST /v1/auth/login`、`POST /v1/auth/refresh`、`POST /v1/auth/logout`；access token 15 分钟，refresh 轮换，Cookie 属性按架构文档设置。
- 依赖：I1-T1。
- 验证清单：
  - [x] 正确凭据返回 200，响应体不含 refresh token 明文。
  - [x] 错误密码返回 401，提示不区分账号不存在与密码错误。
  - [x] 连续刷新两次，第一次的 refresh token 第二次使用时返回 401。
  - [x] 登出后使用原 access token 访问受保护接口返回 401。
- 验收标准：登录、刷新、登出、过期四条路径的返回码与 Cookie 属性全部符合约定；响应头包含 `Cache-Control: no-store`。

#### I1-T3 租户、项目、成员与角色模型

- 内容：`tenants`、`projects`、`memberships`、`membership_projects`、`roles`、`membership_roles`、`role_permissions` 表与 seed；系统角色为客服、客服主管、外包坐席。
- 依赖：I0-T3。
- 验证清单：
  - [x] 同一用户可加入两个租户，`(tenant_id, user_id)` 唯一约束生效。
  - [x] 成员只被授予项目 A 时，项目 B 的请求返回 403。
  - [x] `X-Project-Id` 缺失时，依赖项目的接口返回 400。
  - [x] 种子脚本重复执行不产生重复角色或重复授权。
- 验收标准：跨租户、跨项目、缺项目头三种场景行为符合上述返回码；seed 连续执行三次数据量不变。

#### I1-T4 权限求值与全局 Guard

- 内容：`can(actor, action, resource, field?)`、`@RequirePermission` 元数据、`PolicyGuard`、默认拒绝、权限缓存与变更后主动失效。
- 依赖：I1-T3。
- 验证清单：
  - [x] 所有业务写接口声明 `@RequirePermission`，未声明的写接口由 CI 检查失败。
  - [x] 角色缺少 `ticket:create` 时调用创建接口返回 403。
  - [x] 移除角色授权后，不等待缓存过期，下一次请求即返回 403。
  - [x] 权限服务异常时请求被拒绝而不是放行。
- 验收标准：四条路径均可复现；任何权限判断失败都表现为拒绝，不存在"异常即通过"的分支。

#### I1-T5 字段级权限、投影与写入白名单

- 内容：`field_policies` 表、读取投影、写入白名单、手机号与金额脱敏器、`GET /v1/me/permissions`。
- 依赖：I1-T4。
- 验证清单：
  - [x] 外包坐席读取资源时响应体不含 `internalNote`、`refundAmount` 字段，而不是返回 `null`。
  - [x] 客服写入 `refundAmount` 返回 403 `FIELD_DENIED`，数据未变化。
  - [x] 请求体携带未声明字段返回 400，并在 `details` 中指出字段名。
  - [x] 手机号按角色返回完整值或后四位，格式统一。
- 验收标准：字段的三种状态（完整、脱敏、缺失）与策略表逐条对应；响应断言使用字段存在性而非空值。

#### I1-T6 RLS 策略与数据库角色隔离

- 内容：对所有含 `tenant_id` 的表启用 RLS 与 `FORCE ROW LEVEL SECURITY`；`app_rw` 无 `BYPASSRLS`；事务内设置 `app.tenant_id`；worker 角色按批次设置上下文。
- 依赖：I1-T3。
- 验证清单：
  - [x] 用 `app_rw` 连接并设置租户 A，查询结果只含 A 的数据。
  - [x] 未设置 `app.tenant_id` 时查询返回空集而不是报错或全量数据。
  - [x] 用 `app_rw` 执行 `ALTER TABLE` 被拒绝。
  - [x] 尝试插入 `tenant_id` 为 B 的数据（当前上下文为 A）被策略拒绝。
- 验收标准：四个场景在集成测试中通过；策略覆盖所有业务表，新增表遗漏 RLS 时 CI 检查失败。

#### I1-T7 前端登录、租户切换与越权用例

- 内容：登录页、租户选择、会话恢复、权限驱动的菜单与按钮、401 自动刷新、403 提示；Playwright `@permissions` 套件。
- 依赖：I1-T2、I1-T5。
- 验证清单：
  - [x] 刷新页面后登录态保持，access token 不出现在 localStorage。
  - [x] 切换租户后菜单与字段展示随之变化。
  - [x] 隐藏"内部备注"入口后，直接调用接口仍返回 403，用例有断言。
  - [x] 跨租户访问工单详情（用占位资源）返回 404 页面而非数据泄露。
- 验收标准：`pnpm exec playwright test -g @permissions` 全部通过；用例同时执行 UI 操作与接口直调，证明隐藏不等于授权。

## 5 I2 工单核心与审计

### 5.1 迭代目标

交付可用的工单闭环：创建、列表、详情、状态流转、公开回复与内部备注、变更审计。重复提交不会产生第二张工单，两个坐席同时修改同一工单时后提交者收到冲突提示，任何字段变更都能追溯到人、时间与请求。

### 5.2 交付边界

### 5.3 独立部署验证

  - [ ] 两个 Worker 实例同时运行，没有重复投递。

#### I4-T2 限流与 Redis 降级

- 内容：登录双维度限流、写接口与读接口分档限流、`429` 与 `Retry-After`、Redis 不可用时切换本机内存计数并告警。
- 依赖：I1 出口。
- 验证清单：
  - [ ] 登录连续失败 5 次后锁定 10 分钟，第 6 次返回 429。
  - [ ] 写接口超过每分钟 60 次返回 429，`Retry-After` 为剩余秒数。
  - [ ] 停掉 Redis 后受保护接口仍可用，限流按实例内存生效。
  - [ ] 限流键包含租户，租户 A 的突发流量不影响租户 B。
- 验收标准：阈值可配置且与架构文档一致；降级期间日志有明确告警；Redis 恢复后自动回到集中计数。

#### I4-T3 日志、指标与告警

- 内容：`requestId` 贯穿日志，RED 指标，连接池、慢查询、Outbox 积压、幂等 `PENDING` 四个业务指标，告警规则与排查入口。
- 依赖：I4-T1。
- 验证清单：
  - [ ] 同一请求的访问日志与错误日志可通过 `requestId` 关联。
  - [ ] 指标按路由与租户打标签，可在仪表盘按租户筛选。
  - [ ] 慢查询超过 500ms 记录 SQL 指纹，不记录参数值。
  - [ ] 触发 5xx 告警后能收到通知，通知中含排查链接。
- 验收标准：四条可演示；日志中不出现密码、token、完整手机号；告警规则与文档中的阈值一致。

#### I4-T4 安全加固

- 内容：HSTS、CSP、`X-Content-Type-Options`、`Referrer-Policy`；富文本清洗；密钥文件注入；依赖漏洞扫描与高危阻断。
- 依赖：I3 出口。
- 验证清单：
  - [ ] 响应头包含全部约定项，CSP 不包含 `unsafe-eval`。
  - [ ] 提交带 `<script>` 的工单正文，详情页只显示文本，无脚本执行。
  - [ ] 仓库与镜像中不存在真实密钥，扫描任务无高危项。
  - [ ] 登出、改密、禁用成员后旧会话立即失效。
- 验收标准：安全头由自动化用例断言；XSS 用例在 Playwright 中通过；高危依赖阻断发布。

#### I4-T5 备份、恢复与演练

- 依赖：I4-T3。
- 验证清单：
  - [ ] 备份任务按日执行，产物可下载并校验完整性。
  - [ ] 在隔离环境恢复后，可登录、可查工单、可查审计。
  - [ ] 恢复耗时与数据截止时间记录在案。
  - [ ] 恢复过程不影响生产库。
- 验收标准：一次完整演练有记录、有结论、有遗留问题；恢复后的数据条数与备份时点一致。

#### I4-T6 性能验证

- 内容：按架构文档的性能预算压测列表、详情、创建、权限求值、知识库检索；记录 P95 与慢查询。
- 依赖：I2、I3 出口。

  - [ ] 工单列表 P95 ≤ 300ms，详情 ≤ 200ms，创建 ≤ 400ms。
  - [ ] 权限求值 P95 ≤ 5ms，缓存命中率符合预期。
  - [ ] 知识库检索 P95 ≤ 500ms。
  - [ ] 压测期间无连接池耗尽、无 5xx 比例上升。
- 验收标准：五项指标在预发环境实测达标；未达标项附原因与处置，不以"环境差异"直接豁免。

#### I4-T7 全量回归与发布验收

  - [ ] 回滚到上一镜像标签后服务可启动，数据兼容。
  - [ ] 发布检查单逐项签字，无未关闭的高优问题。
- 验收标准：两条迁移路径与回滚路径均有执行记录；发布检查单完整；遗留问题明确责任人与处理方式。

## 9 计划维护规则

任务新增或拆分时，必须在所属迭代内补充任务编号、依赖、验证清单与验收标准，并同步更新状态汇总表的任务总数。新增任务不得降低迭代出口标准，也不得把未完成任务挪到下一个迭代来换取当前迭代通过。

已完成任务的验收标准不允许事后修改。验收过程中发现标准缺失，应新增补充任务并重新验收，而不是回填标准后直接标记通过。

任务被驳回时保留原登记行，结论改为不通过并写明原因，修复后新增一行登记，不覆盖历史记录。迭代出口验收失败时，迭代状态回到开放，直到全部问题关闭并重新登记。
